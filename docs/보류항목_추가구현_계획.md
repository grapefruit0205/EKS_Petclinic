## D1. HTTPS · 커스텀 도메인

### 목표
`https://clinic.mission-critical.site` 로 서비스하고, API Gateway 기본 `execute-api` 엔드포인트를 비활성화한다.
ALB 도 HTTPS 443 + ACM 인증서로 올려 VPC Link → ALB 구간을 TLS 로 보호한다(설계안 6.2).

### 선행조건 (외부 · 사용자 작업)
가비아에서 `mission-critical.site` 의 네임서버를 아래로 교체한다.

```text
ns-1089.awsdns-08.org
ns-1713.awsdns-22.co.uk
ns-390.awsdns-48.com
ns-789.awsdns-34.net
```

교체 전 상태(실측): 기존 위임 NS `ns-42.awsdns-05.com` 등은 **삭제된 Route53 존**을 가리켜 `REFUSED`, 공개 조회는 `SERVFAIL`.
ACM 인증서 `clinic.mission-critical.site` 는 이미 생성되어 `PENDING_VALIDATION` 이고, 검증 CNAME 은 kdt5 존에 존재한다.

### 변경 대상
| 파일 | 변경 |
|---|---|
| `terraform/terraform.tfvars` | `enable_custom_domain = true` |
| `terraform/edge/terraform.tfvars` | `custom_domain_enabled = true` |
| `k8s/30-ingress.yaml` | `listen-ports` 를 `[{"HTTPS":443}]` 로, `certificate-arn` 추가, `ssl-redirect` 활성 |

### 구현
```bash
# 1) ACM 검증 대기 (검증 CNAME 이 공개 해석되면 수 분 내 ISSUED)
cd EKS_Project/terraform
sed -i 's/^enable_custom_domain = false/enable_custom_domain = true/' terraform.tfvars
terraform apply

# 2) edge: 커스텀 도메인 + Route53 A(alias)
cd edge
sed -i 's/^custom_domain_enabled = false/custom_domain_enabled = true/' terraform.tfvars
terraform apply
```

Ingress(HTTPS 전환):
```yaml
annotations:
  alb.ingress.kubernetes.io/listen-ports: '[{"HTTPS":443}]'
  alb.ingress.kubernetes.io/certificate-arn: arn:aws:acm:ap-northeast-2:123456789012:certificate/3335292a-8a8c-4da1-a8a6-970167fad9d7
  alb.ingress.kubernetes.io/ssl-redirect: "443"
```
전환 후 `k8s/30-ingress.yaml` 의 기존 HTTP 80 리스너 annotation 은 제거하고,
`terraform/modules/security` 의 임시 80 규칙(`alb_from_vpclink_80`, `vpclink_to_alb_80`)을 443 만 남기고 삭제한다.

API Gateway 통합 TLS(설계안 6.2: `tlsConfig.serverNameToVerify`):
```hcl
# terraform/edge/main.tf 의 aws_apigatewayv2_integration.alb 안에
tls_config {
  server_name_to_verify = local.foundation.app_fqdn
}
```

### 완료 판정
- `aws acm describe-certificate` → `Status: ISSUED`
- `curl -I https://clinic.mission-critical.site/` → `HTTP/2 200`
- `curl` 로 인증서 CN/SAN 확인 → `clinic.mission-critical.site`
- `aws apigatewayv2 update-api --disable-execute-api-endpoint` 적용 후 기존 `abcdefghij` URL 이 403
- `dig +short clinic.mission-critical.site` → API Gateway 리전 도메인

### 위험·롤백
- NS 전파 전에 `enable_custom_domain=true` 로 apply 하면 `aws_acm_certificate_validation` 이 최대 75분 대기 후 실패한다. **전파 확인 후** 전환한다.
- 기존 존이 이미 죽어 있어 레코드 유실 위험은 없다.
- 롤백: `custom_domain_enabled=false` 로 되돌리고 execute-api 엔드포인트를 다시 활성화.

## D2. NetworkPolicy (default-deny + allowlist)

### 목표
namespace `petclinic-dev` 에 default-deny 를 적용하고, 설계안 4.2 의 업무 흐름만 허용한다.
VPC CNI NetworkPolicy 는 이미 활성(`enableNetworkPolicy=true`)이다.

### 선행조건
없음. 단 **kubelet probe 와 노드→Pod 트래픽 예외**를 먼저 설계해야 한다(가장 흔한 실패 원인).

### 변경 대상
신규 파일 `k8s/40-networkpolicy.yaml`

### 구현
```yaml
# 1) default deny (ingress + egress)
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: default-deny-all
  namespace: petclinic-dev
spec:
  podSelector: {}
  policyTypes: [Ingress, Egress]
---
# 2) DNS 허용 (모든 Pod → kube-system CoreDNS, UDP/TCP 53)
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: allow-dns-egress
  namespace: petclinic-dev
spec:
  podSelector: {}
  policyTypes: [Egress]
  egress:
    - to:
        - namespaceSelector:
            matchLabels: { kubernetes.io/metadata.name: kube-system }
      ports:
        - { protocol: UDP, port: 53 }
        - { protocol: TCP, port: 53 }
---
# 3) App: ingress 는 web Pod 8080 + 노드/프로브(10250/8080), egress 는 RDS 3306
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: app-allow
  namespace: petclinic-dev
spec:
  podSelector:
    matchLabels: { app.kubernetes.io/component: app }
  policyTypes: [Ingress, Egress]
  ingress:
    - from:
        - podSelector:
            matchLabels: { app.kubernetes.io/component: web }
      ports: [{ protocol: TCP, port: 8080 }]
    # kubelet probe 는 노드 IP 에서 온다 → VPC CIDR 허용 (설계안 4.2 주의사항)
    - from:
        - ipBlock: { cidr: 10.20.0.0/16 }
      ports: [{ protocol: TCP, port: 8080 }]
  egress:
    - to:
        - ipBlock: { cidr: 10.20.80.0/23 }   # isolated data 서브넷
      ports: [{ protocol: TCP, port: 3306 }]
---
# 4) Web: ingress 는 ingress 서브넷(ALB), egress 는 app-svc 8080
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: web-allow
  namespace: petclinic-dev
spec:
  podSelector:
    matchLabels: { app.kubernetes.io/component: web }
  policyTypes: [Ingress, Egress]
  ingress:
    - from:
        - ipBlock: { cidr: 10.20.8.0/23 }    # private ingress 서브넷
      ports:
        - { protocol: TCP, port: 8080 }
        - { protocol: TCP, port: 8081 }
  egress:
    - to:
        - podSelector:
            matchLabels: { app.kubernetes.io/component: app }
      ports: [{ protocol: TCP, port: 8080 }]
```

### 완료 판정 (음성 테스트 포함)
| 시험 | 기대 |
|---|---|
| Web Pod → `app-svc:8080` | **성공** |
| Web Pod → RDS 3306 | **실패** (연결 거부/타임아웃, 종료코드로 구분) |
| 임의 Pod(`kubectl run tmp`) → `app-svc:8080` | **실패** |
| 임의 Pod → RDS 3306 | **실패** |
| ALB target health | **healthy 유지** (프로브 차단 없음) |
| App Pod 재시작 후 readiness | **정상 전환** |

> `실패 || echo BLOCKED` 같은 형태로 통과 처리하지 말 것. **정상 대조군(같은 대상의 허용 경로 성공)** 과 함께 종료코드·흐름 관측으로 구분한다.
> NetworkPolicy 는 여러 정책의 **허용 합집합**이므로 정책 전체와 라벨 수정 RBAC 도 함께 점검한다.

### 위험·롤백
- 잘못 적용하면 Pod 가 통째로 NotReady 가 된다(프로브 차단). staging namespace 에서 먼저 검증한다.
- 롤백: `kubectl delete -f k8s/40-networkpolicy.yaml` (default-deny 삭제로 즉시 원복).

## D3. migration Job

### 목표
스키마 변경을 **1회성 Job** 으로 분리하고 이력(schema history)을 남긴다. 앱 Pod 기동과 분리해 replica 증가 시 DDL 중복을 막는다.

### 현재 상태
관리 EC2 에서 `mysql` 클라이언트로 1회 적용했다. 대상 SQL 은 멱등(`CREATE TABLE IF NOT EXISTS`, `INSERT IGNORE`)이지만 이력이 없다.

### 변경 대상
- 신규 `k8s/50-migration-job.yaml`
- (선택) Flyway 도입 시 앱 이미지에 `flyway-core` + `db/migration/V1__baseline.sql` 추가

### 구현 (Flyway 없이 최소 구현)
```yaml
apiVersion: batch/v1
kind: Job
metadata:
  name: db-migrate-v1
  namespace: petclinic-dev
spec:
  backoffLimit: 1
  ttlSecondsAfterFinished: 86400
  template:
    spec:
      restartPolicy: Never
      serviceAccountName: petclinic-migration   # IRSA: migration secret 읽기 전용
      containers:
        - name: migrate
          image: 123456789012.dkr.ecr.ap-northeast-2.amazonaws.com/petclinic-app:1.0.6
          command: ["/bin/bash", "-c"]
          args:
            - |
              set -euo pipefail
              HOST=$(sed -n 's/^jdbc\.url=jdbc:mysql:\/\/\([^:/]*\).*/\1/p' /etc/petclinic/data-access.properties)
              # 이 Job 은 migration 계정/파일을 별도 Secret(migration-config)으로 마운트한다
              mysql --ssl -h "$HOST" -u "$DB_USER" -p"$DB_PASS" petclinic \
                -e "CREATE TABLE IF NOT EXISTS schema_history (
                      version VARCHAR(32) PRIMARY KEY,
                      applied_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP);"
              mysql --ssl -h "$HOST" -u "$DB_USER" -p"$DB_PASS" petclinic < /migration/V1__baseline.sql
              mysql --ssl -h "$HOST" -u "$DB_USER" -p"$DB_PASS" petclinic \
                -e "INSERT IGNORE INTO schema_history(version) VALUES ('V1');"
          envFrom:
            - secretRef: { name: migration-credentials }
          volumeMounts:
            - { name: sql, mountPath: /migration }
      volumes:
        - name: sql
          configMap: { name: migration-sql }
```

### 완료 판정
- `kubectl -n petclinic-dev get job db-migrate-v1` → `Complete 1/1`
- 재실행해도 오류 없이 성공(멱등) — `kubectl delete job` 후 재적용
- `SELECT * FROM schema_history;` 에 `V1` 1건
- App 재배포 시 DDL 로그가 **없음** (startup 초기화 차단 확인)

### 위험·롤백
- 파괴적 변경은 expand/contract 2단계로 나눈다. SQL 자동 역실행을 롤백으로 가정하지 않는다.
- 실패 시 이전 앱 배포를 유지하고 Job 로그를 확인한다.

## D4. 앱 `/health/live` · `/health/ready`

### 목표
DB 장애 시 `live` 는 200 유지, `ready` 는 503 으로 트래픽에서 제외한다(설계안 5.3).

### 현재 상태
`/`(보호자 수 조회 = DB 접근)를 readiness 로, TCP 8080 을 liveness 로 사용 중. 동작하지만 의도가 섞여 있다.

### 변경 대상
- 신규 `src/main/java/org/springframework/samples/petclinic/web/HealthController.java`
- `k8s/10-app.yaml` 의 probe 경로

### 구현
```java
package org.springframework.samples.petclinic.web;

import org.springframework.http.HttpStatus;
import org.springframework.http.ResponseEntity;
import org.springframework.jdbc.core.JdbcTemplate;
import org.springframework.web.bind.annotation.GetMapping;
import org.springframework.web.bind.annotation.RestController;

@RestController
public class HealthController {

    private final JdbcTemplate jdbcTemplate;

    public HealthController(JdbcTemplate jdbcTemplate) {
        this.jdbcTemplate = jdbcTemplate;
    }

    // 프로세스 생존만 판단 — DB 장애와 분리한다
    @GetMapping("/health/live")
    public ResponseEntity<String> live() {
        return ResponseEntity.ok("ok");
    }

    // DB 접근 성공 여부로 트래픽 수용 여부를 판단한다
    @GetMapping("/health/ready")
    public ResponseEntity<String> ready() {
        try {
            jdbcTemplate.queryForObject("SELECT 1", Integer.class);
            return ResponseEntity.ok("ok");
        } catch (Exception e) {
            return ResponseEntity.status(HttpStatus.SERVICE_UNAVAILABLE).body("db unavailable");
        }
    }
}
```
> `org.springframework.samples.petclinic.web` 는 `mvc-core-config.xml` 의 component-scan 대상이므로 별도 XML 등록이 필요 없다(확인 후 적용).

Deployment probe 변경:
```yaml
startupProbe:   { httpGet: { path: /health/live,  port: http }, failureThreshold: 30, periodSeconds: 10 }
livenessProbe:  { httpGet: { path: /health/live,  port: http }, periodSeconds: 20, failureThreshold: 4 }
readinessProbe: { httpGet: { path: /health/ready, port: http }, periodSeconds: 10, timeoutSeconds: 3 }
```
Web(nginx) 8080 에서 `/health/` 를 404 로 차단하는 규칙은 그대로 유지한다(외부 노출 금지).

### 완료 판정
- 기동 직후 `kubectl get pod` → `Ready True`
- RDS SG 를 임시로 닫거나 DB 를 중지 → `ready` **503**, `live` **200**, Pod 는 Running 유지, Service endpoint 에서 제외
- DB 복구 후 수십 초 내 `ready` **200** 자동 회복
- ALB target health 가 unhealthy → healthy 로 복귀

### 위험·롤백
- `ready` 가 DB 를 직접 치므로 DB 장애 시 전 Pod 가 동시에 빠진다. DB pool 예산과 재시도 간격을 함께 조정한다.
- 롤백: probe 경로를 `/` 로 되돌린다.

## D5. HPA + Cluster Autoscaler

### 목표
Pod 수(HPA)와 노드 수(Cluster Autoscaler)를 부하에 따라 자동 조정한다. 설계안 7.1: App HPA 2~6, CPU request 대비 60%.

### 선행조건
- `metrics-server` 설치됨(현재 Running)
- Cluster Autoscaler IRSA 역할 생성됨(`petclinic-dev-cluster-autoscaler-role`)
- **ASG 태그 필요**: `k8s.io/cluster-autoscaler/enabled=true`, `k8s.io/cluster-autoscaler/petclinic-dev=owned`

### 변경 대상
- `terraform/variables.tf` 의 `node_groups` 에 CA 태그 추가 → `terraform/modules/eks` 가 노드그룹 태그로 전달
- 신규 `k8s/60-hpa.yaml`

### 구현
Terraform(노드그룹 태그):
```hcl
# terraform/eks.tf 또는 modules/eks 에서 노드그룹 tags 에 추가
tags = merge(var.tags, {
  "k8s.io/cluster-autoscaler/enabled"              = "true"
  "k8s.io/cluster-autoscaler/${var.cluster_name}"  = "owned"
})
```
HPA:
```yaml
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: app-hpa
  namespace: petclinic-dev
spec:
  scaleTargetRef: { apiVersion: apps/v1, kind: Deployment, name: app }
  minReplicas: 2
  maxReplicas: 6
  metrics:
    - type: Resource
      resource:
        name: cpu
        target: { type: Utilization, averageUtilization: 60 }
  behavior:
    scaleDown:
      stabilizationWindowSeconds: 300
```
Cluster Autoscaler(Helm):
```bash
helm repo add autoscaler https://kubernetes.github.io/autoscaler
helm upgrade --install cluster-autoscaler autoscaler/cluster-autoscaler -n kube-system \
  --set autoDiscovery.clusterName=petclinic-dev \
  --set awsRegion=ap-northeast-2 \
  --set rbac.serviceAccount.name=cluster-autoscaler \
  --set "rbac.serviceAccount.annotations.eks\.amazonaws\.com/role-arn=<cluster-autoscaler-role-arn>" \
  --set extraArgs.balance-similar-node-groups=true \
  --set extraArgs.skip-nodes-with-system-pods=false
```
> GitOps 로 관리한다면 HPA 가 관리하는 `replicas` 필드를 배포 매니페스트에서 제거해 수동 명령과 경쟁하지 않게 한다.

### 완료 판정
- `kubectl get hpa` → TARGETS 에 실제 CPU% 표시
- 부하 인가 시 `REPLICAS` 2 → 증가, 부하 중단 후 안정화 윈도우 뒤 감소
- Pending Pod 발생 시 CA 가 대상 MNG 를 증가시키고 노드가 Ready
- 최대 노드 수/DB 연결 수 예산을 넘지 않음

### 위험·롤백
- DB 가 병목인데 App replica 만 늘리면 연결 수가 폭증한다. 연결 수 예산(A: 최대 6×pool, rolling surge 포함)을 먼저 계산한다.
- CA 와 Karpenter 를 같은 노드그룹에 중복 적용하지 않는다.

## D6. Cognito OIDC 인증 · 인가 · CSRF · 공유 세션

### 목표
로그인 없이는 데이터 접근·쓰기가 불가능하게 만들고, Pod 교체에도 로그인 상태를 유지한다.
읽기/쓰기 역할을 분리한다(설계안 5.1).

### 현재 상태
인프라는 준비됨 — Cognito User Pool `petclinic-dev-users`, 앱 클라이언트(confidential, secret 有), Hosted UI 도메인, 그룹 `petclinic-readers`/`petclinic-writers`, Secret `petclinic-dev/app/cognito`. **애플리케이션 코드만 없다.**

### 변경 대상 (애플리케이션)
| 영역 | 작업 |
|---|---|
| 의존성 | `spring-security-web`, `spring-security-config`, `spring-security-oauth2-client`, `spring-session-jdbc` |
| XML | `security-config.xml` 신규 + `web.xml` contextConfigLocation 에 추가 |
| Java | `SecurityConfig`(또는 XML bean), `OidcUserService` 매핑, 역할 변환기 |
| JSP | 로그인/로그아웃 링크, 모든 폼에 CSRF hidden 토큰 |
| DB | Spring Session 테이블(`SPRING_SESSION`, `SPRING_SESSION_ATTRIBUTES`) 별도 schema |
| 설정 | `/etc/petclinic/oidc.properties`(issuer-uri, client-id, client-secret, redirect-uri) — 기존 외부 파일 주입 방식 재사용 |

### 구현 개요
```text
1) Secret petclinic-dev/app/cognito 를 app-config 와 같은 방식으로 파일 주입
   → /etc/petclinic/oidc.properties
2) issuer-uri = https://cognito-idp.ap-northeast-2.amazonaws.com/<pool-id>
   redirect-uri = https://clinic.mission-critical.site/login/oauth2/code/cognito   (D1 선행)
3) SecurityFilterChain:
   - /health/**, /resources/**, /webjars/** permitAll
   - GET /, /owners/**, /vets** : 인증 필요(읽기)
   - POST/PUT/DELETE(등록·수정) : ROLE_writers 필요
   - oauth2Login() + logout + CSRF 활성
4) 공유 세션: @EnableJdbcHttpSession + DataSource 공유, 쿠키 Secure/HttpOnly/SameSite=Lax/Path=/
5) Gateway UI route 는 인증 NONE 유지 — 인증은 App 이 담당
```

### 완료 판정
| 시험 | 기대 |
|---|---|
| 비로그인 `GET /owners/find` | 로그인 페이지로 리다이렉트 |
| 로그인 → 보호자 검색·등록·수정·방문 등록 | **정상**, DB 반영 확인 |
| readers 그룹 계정으로 등록 시도 | **403** |
| CSRF 토큰 제거 후 POST | **403** |
| 로그인 후 App Pod 2개를 순차 재시작 | 세션 유지(Pod 교체에도 로그아웃 안 됨) |
| 로그아웃 | 세션 무효화, 보호 페이지 재접근 차단 |
| 위조 `X-Forwarded-Proto: http` 주입 | 리다이렉트/쿠키가 여전히 HTTPS |

### 위험·롤백
- 원본 UI 는 폼 기반이라 CSRF 토큰 누락 시 **모든 쓰기가 403** 이 된다. JSP 전체 폼 점검이 필수.
- 인증 도입 전까지 현재 배포는 **무인증 공개 상태**이므로 외부 공개하지 않는다.
- 롤백: security 필터 체인을 비활성화한 이전 이미지 digest 로 되돌린다.

## D7. Secrets Store CSI Driver

### 목표
DB 비밀을 Kubernetes Secret 복사본이 아니라 **Secrets Manager 에서 직접 파일로 마운트**하고 rotation 절차를 확립한다(설계안 4.3).

### 현재 상태
Secrets Manager + IRSA + EKS secrets KMS 암호화는 적용. 런타임은 `app-config` 라는 Kubernetes Secret 을 파일로 마운트한다.

### 변경 대상
- Helm: `secrets-store-csi-driver` + `secrets-store-csi-driver-provider-aws`
- `k8s/10-app.yaml`: volume 을 CSI 로 교체
- IRSA: 기존 `petclinic-dev-app-role` 재사용

### 구현
```bash
helm repo add secrets-store-csi-driver https://kubernetes-sigs.github.io/secrets-store-csi-driver/charts
helm upgrade --install csi-secrets-store secrets-store-csi-driver/secrets-store-csi-driver \
  -n kube-system --set syncSecret.enabled=true --set enableSecretRotation=true \
  --set rotationPollInterval=2m

helm repo add aws-secrets-manager https://aws.github.io/secrets-store-csi-driver-provider-aws
helm upgrade --install secrets-provider-aws aws-secrets-manager/secrets-store-csi-driver-provider-aws \
  -n kube-system
```
```yaml
# SecretProviderClass
apiVersion: secrets-store.csi.x-k8s.io/v1
kind: SecretProviderClass
metadata:
  name: petclinic-db
  namespace: petclinic-dev
spec:
  provider: aws
  parameters:
    usePodIdentity: "false"
    objects: |
      - objectName: "petclinic-dev/app/db"
        objectType: "secretsmanager"
        jmesPath:
          - { path: "username", objectAlias: "db-username" }
          - { path: "password", objectAlias: "db-password" }
```
```yaml
# Deployment volume
volumes:
  - name: db-secret
    csi:
      driver: secrets-store.csi.k8s.io
      readOnly: true
      volumeAttributes: { secretProviderClass: petclinic-db }
containers:
  - volumeMounts:
      - { name: db-secret, mountPath: /mnt/secrets, readOnly: true }
```

### 완료 판정
- `/mnt/secrets/db-password` 파일 존재, 권한이 non-root UID(10001)로 읽기 가능
- 잘못된 SA 로 마운트 시도 → **거부**
- Secrets Manager 값 rotation 후 2분 내 파일 갱신 확인
- **파일 갱신 ≠ 앱 재연결**: pool 재연결 또는 rolling restart 절차를 문서화하고 실제 재접속까지 확인

### 위험·롤백
- `syncSecret` 로 Kubernetes Secret 을 동기화하면 결국 Secret 사본이 생긴다. 파일 마운트만 쓸지 결정한다.
- 롤백: volume 을 기존 `app-config` Secret 으로 되돌린다.

## D8. 부하 · 장애 · 복구 시험

### 목표
설계안 8장 Phase 9~10 과 인수 테스트 T09~T11 을 실제 증거로 남긴다.

### 시험 목록과 판정 기준
| ID | 시험 | 통과 기준 | 증빙 |
|---|---|---|---|
| T09 | 부하 | 합의 요청률(예: 20 rps, 15분)에서 성공률 ≥99%, 동적 GET p95 ≤1초, HPA·노드 증가 관측 | 부하 도구 출력, HPA/노드 그래프 |
| T10 | 드레인/롤아웃 | `maxUnavailable 0` 롤아웃과 node drain 중 오류율이 허용 예산 이내, 연속 요청 성공 | 요청 로그, 종료 시간 |
| T11 | RDS 장애/복구 | failover 후 재연결, PITR 로 **별도 DB** 복원 후 건수·기능 검증, RPO/RTO 실측 기록 | RDS 이벤트, 복원 검증 로그 |

### 절차 원칙
- 장애는 **한 번에 하나씩** 주입한다(Pod 삭제 → DB 접속 차단 → node drain → AZ 장애 모의 → rolling update → Secret rotation).
- Multi-AZ 고가용성과 백업 복구를 구분한다. failover 성공을 PITR 복구 성공으로 쓰지 않는다.
- 복원은 **별도 DB 인스턴스**로 수행하고 원본에 덮어쓰지 않는다.
- RPO ≤5분 / RTO ≤60분은 **목표 제안**이며 실측값과 차이를 기록한다.

### 완료 판정
- 위 표의 증빙이 모두 첨부됨. 미충족 항목은 영향·소유자·해결 일정을 명시.

## D9. Terraform state 원격화

### 목표
state 를 암호화·잠금·버전 보관이 되는 S3 + DynamoDB 로 옮긴다(설계안 7.2).

### 구현
```hcl
# terraform/versions.tf
backend "s3" {
  bucket         = "petclinic-tfstate-123456789012"
  key            = "foundation/terraform.tfstate"
  region         = "ap-northeast-2"
  dynamodb_table = "petclinic-tfstate-lock"
  encrypt        = true
}
```
- 버킷: 버전 관리 + SSE-KMS + 퍼블릭 액세스 차단
- `terraform init -migrate-state`

### 완료 판정
- `terraform state list` 정상, `plan` 변경 없음
- 동시 apply 시 잠금 동작 확인
- state 에 평문 DB 비밀번호가 없음을 재확인(현재 확인됨)

## 공통 검증 원칙

- **"배포 성공"과 "기능 성공"을 구분한다.** `Pod Running`, `target healthy`, `Programmed` 는 기능 증거가 아니다.
- 음성 테스트에는 **정상 대조군**을 둔다. 차단된 이유가 정책인지 DNS·이미지·명령 실패인지 종료코드와 흐름으로 구분한다.
- 실행하지 않은 시험을 성공으로 표시하지 않는다. 미수행은 미수행으로 남긴다.
- 모든 신규 리소스에 `Project / Environment / Owner / ExpiresAt` 태그를 유지한다.
